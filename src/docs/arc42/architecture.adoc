== Introduction and Goals

=== Requirements Overview

mediform is a prototype tool for hospital staff to create, manage, and
distribute FHIR-backed questionnaires through a human-readable,
AI-generatable DSL format (`.mediform`).

The system serves three user groups:

Patients:: Fill out and review questionnaires via a patient-facing app.
Nurses:: Create questionnaires by prompting an external LLM, then import, edit, preview, and submit them for review via an employee app.
Trained Staff:: Review, approve, publish, and retire questionnaires; oversee quality via the employee app.

The core innovation is the `.mediform` format: a markdown-ish DSL that
is readable by non-technical staff, generatable by LLMs (including FHIR
metadata like LOINC and SNOMED codes), and compilable to FHIR resources
at a system boundary.

Full requirements are in `src/docs/specs/prd.adoc`.

=== Quality Goals

[cols="1,3,2"]
|===
| Priority | Quality Goal | Scenario

| 1 | Format readability | A nurse with no technical training reads a `.mediform` file and understands what the questionnaire asks within 2 minutes.
| 2 | AI generatability | An LLM produces a valid, complete `.mediform` file (including FHIR codes) from a natural-language prompt in a single pass.
| 3 | FHIR compliance | Every published questionnaire compiles to a valid FHIR R4 Questionnaire resource. Every submitted response compiles to a valid QuestionnaireResponse with correct Observations.
| 4 | Extensibility | A developer adds a new custom question type (e.g., drawing accuracy) by writing a JS function embedded in the format, without modifying the system.
| 5 | Prototype velocity | A single developer can build and demonstrate the end-to-end flow within weeks, not months.
|===

=== Stakeholders

[cols="1,2,2"]
|===
| Stakeholder | Role | Expectations

| Sebastian | Product owner, developer | Working prototype that proves the format design. Clean architecture that can evolve.
| Nurses (future) | Primary content creators | Simple, non-technical interface for managing questionnaires.
| Hospital IT (future) | Operations | FHIR-compliant data that integrates with existing systems.
| Patients (future) | End users | Clear, mobile-friendly forms.
|===

== Architecture Constraints

=== Technical Constraints

[cols="1,3"]
|===
| Constraint | Rationale

| Runtime: Bun | Modern, fast JS/TS runtime. Chosen for prototype speed and DX.
| Language: TypeScript (strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes) | Type safety, modern ecosystem. The extra flags catch array-index and optional-property bugs at compile time.

== Solution Strategy

=== Key Design Decisions

[cols="1,3,2"]
|===
| Decision | Description | Rationale

| Custom DSL over FHIR JSON
| Define a markdown-ish `.mediform` format instead of using FHIR Questionnaire JSON directly.
| FHIR JSON is too verbose and technical for nurses. The DSL is human-first; FHIR is a compilation target.

| Compile at the boundary
| The `.mediform` format is the source of truth. FHIR resources are generated at publish time and response submission time.
| Keeps the internal model simple. FHIR complexity is isolated to the compiler.

| AI generates everything
| The LLM produces the complete `.mediform` file including FHIR codes (LOINC, SNOMED). No enrichment layer.
| Simplifies the pipeline. The format is designed to be LLM-friendly.

| Custom renderers in iframes
| Complex question types (e.g., drawing accuracy) are embedded JS that runs in a sandboxed iframe. The renderer's only contract is `onValue(result)`.
| Separates rendering from semantics. Extensible without modifying the core system. Sandboxing provides safety.

| Single-process monolith
| One Bun process serves the API, the patient SPA, and the employee SPA.
| Simplest deployment for a prototype. No orchestration overhead.

| HAPI FHIR for storage
| All patient data (questionnaires, responses, observations) is stored on HAPI FHIR, not in a local database.
| Offloads data responsibility. Ensures FHIR compliance. Enables third-party interop.

| Questionnaire metadata in local store
| Lifecycle state, author, feedback, and `.mediform` source are stored in SQLite via a repository pattern. FHIR resources are created only at publish/submit time.
| FHIR is not designed for draft/review workflows. Local storage handles lifecycle; FHIR handles clinical data. The repository pattern enables file-based SQLite for dev and in-memory SQLite for tests.

| Type-safe API client via Eden Treaty
| Both Svelte SPAs consume the Elysia API through Eden Treaty, which derives a fully typed client from the server's route definitions.
| Eliminates manual type duplication between backend and frontend. Catches API contract mismatches at compile time.
|===

=== Technology Mapping

[cols="2,2,3"]
|===
| Concern | Technology | Notes

| HTTP server | Elysia | Bun-native, type-safe routes, validation via schema.
| API client | Eden Treaty | Both Svelte SPAs derive a type-safe client from Elysia route definitions. Replaces manual `fetch` wrappers. See ADR-007.
| SPA framework | Svelte | Two separate Svelte SPAs: `apps/patient` and `apps/employee`. Each built with Vite; served as static files by Elysia.
| `.mediform` parser | Custom TypeScript module | Parses YAML frontmatter + markdown-ish body. No external parser dependency expected. Shared types live in `packages/mediform-core`.
| FHIR compiler | Custom TypeScript module | Transforms parsed questionnaire to FHIR R4 JSON. Shared types live in `packages/mediform-core`.
| FHIR client | `fetch` (Bun built-in) | Direct HTTP calls to HAPI FHIR REST API. No FHIR client library needed for prototype.
| Local storage | SQLite via `bun:sqlite` | Questionnaire records, lifecycle state, quality check results. Repository pattern abstracts storage; file-based for dev, `:memory:` for tests. See ADR-009.
| Linter/Formatter | Biome | Single `biome.json` at workspace root. Replaces ESLint + Prettier. See ADR-008.
| Code quality gate | Pre-push hook | Shell script runs Biome lint and format checks on changed files. See ADR-010.
| Custom renderer sandbox | `<iframe sandbox>` | Browser-side. CSP restricts network access.
| Quality checks | Custom TypeScript module | Runs syntax, metadata, code-system, and renderer checks.
|===

== Cross-cutting Concepts

=== The `.mediform` Format as the Central Abstraction

The `.mediform` format is the system's lingua franca.
Every major operation flows through it:

[plantuml]
----
@startuml

rectangle "External LLM" as LLM

LLM -right-> MF : generates
MF -right-> Parser : parses
Parser -right-> AST : produces
AST -down-> Compiler : compiles

AST -right-> Renderer : renders
Renderer -right-> UI : displays

@enduml

The format is:

* The *input* (nurse imports it).
* The *source of truth* (stored in local DB, editable).
* The *compilation source* (compiled to FHIR at publish/submit time).
* The *rendering source* (parsed to produce the patient UI).

=== Questionnaire Lifecycle State Machine

[plantuml]
----
@startuml
title Questionnaire Lifecycle

[*] --> Draft : import / create

Draft --> Draft : edit (save)
Draft --> Review : submit\n[syntax valid,\nmetadata complete,\nquality checks pass]

Review --> Approved : approve
Review --> Draft : request changes\n[feedback attached]
Review --> Rejected : reject\n[reason attached]

Approved --> Published : publish\n[FHIR compilation\nsucceeds]

Published --> Retired : retire\n[confirmation]

Rejected --> [*]
Retired --> [*]

@enduml
----

Status transitions are enforced by the Lifecycle Manager component.
Each transition has preconditions defined by business rules
(BR-013, BR-016, BR-017, BR-019, BR-021, BR-026, BR-030).

=== Custom Renderer Sandboxing

Custom renderers run in the browser inside a sandboxed `<iframe>`.

[cols="1,3"]
|===
| Mechanism | Details

| `<iframe sandbox="allow-scripts">` | No same-origin access, no forms, no popups, no top-level navigation.
| Communication | `postMessage` between host and iframe. Host sends config; iframe sends `onValue(result)`.
| Content Security Policy | `script-src 'unsafe-inline'` (renderer code is inline). No external script loading. No `connect-src` (no network access).
| Value validation | Host validates the received value against the declared `maps-to` type before accepting it.
|===

[plantuml]
----
@startuml
title Custom Renderer Communication

participant "Form Renderer\n(host page)" as Host
participant "Sandboxed Iframe\n(renderer)" as Iframe

Host -> Iframe: postMessage({type: "init",\nconfig: {min: 0, max: 100}})
Iframe -> Iframe: Render UI,\ntrack user interaction
Iframe -> Host: postMessage({type: "value",\nvalue: 87.5})
Host -> Host: Validate value\nagainst maps-to type

@enduml

[cols="2,2,2"]
|===
| `.mediform` Concept | FHIR Resource | Key Fields

| Section (`##` heading) | `Questionnaire.item` (type: group) | text, item[]

=== Error Handling Strategy

[cols="1,3"]
|===
| Layer | Strategy

| `.mediform` parsing | Collect all errors with line numbers. Return them all at once (no fail-fast). Allow partial results for preview.
| API validation | Return 422 with structured error arrays. Each error identifies the field/question and provides a human-readable message.
| FHIR server communication | Return 502 on failure. No retry logic in the prototype. Atomicity via FHIR transaction bundles where supported, otherwise sequential with rollback on failure.
| Custom renderer | Catch errors at the iframe boundary. Display fallback UI. Log errors to console. Never crash the host page.
|===

_(Prototype shortcut: no structured logging, no error reporting service, no retry/circuit-breaker patterns.)_

| FHIR Questionnaire, QuestionnaireResponse, Observation | HAPI FHIR Server. Owned by the FHIR provider.
| Patient identity | Not managed by mediform. _(Prototype shortcut: no patient identity management. Responses are anonymous or link-based.)_

== Architecture Decisions

=== ADR-001: Custom DSL over FHIR Questionnaire JSON

Status:: Accepted
Context:: FHIR Questionnaire is a comprehensive but verbose JSON format. Nurses cannot read or review it. LLMs can generate it but the output is hard to verify.
Decision:: Define a custom `.mediform` DSL that is human-readable and compiles to FHIR at a system boundary.
Consequences:: We must build and maintain a parser and compiler. The format is a new invention that must be documented and tested. But it enables the core value proposition: nurses can read what the AI generated.

=== ADR-002: HAPI FHIR for All Clinical Data Storage

Status:: Accepted
Context:: We need to store questionnaires, responses, and observations. We could use a local database or a FHIR server.
Decision:: Store all clinical data on HAPI FHIR. Use a local SQLite database only for lifecycle metadata (draft state, review feedback, etc.).
Consequences:: Data responsibility is pushed to the FHIR provider. Third-party tools can consume data directly. But we depend on HAPI availability for publish and response submission. Local operations (edit, preview) work without HAPI.

=== ADR-003: Single-Process Monolith

Status:: Accepted
Context:: The system has two SPAs and an API. We could deploy them separately or together.
Decision:: Serve everything from a single Bun process. Elysia serves the API and static SPA assets.
Consequences:: Simplest deployment. No CORS issues. No reverse proxy needed. But no independent scaling of frontend and backend. Acceptable for a prototype.

=== ADR-004: SQLite for Local State

Status:: Accepted (implementation refined in ADR-009)
Context:: Questionnaire lifecycle state, `.mediform` source, and quality check results need persistent storage. FHIR is not designed for draft/review workflows.
Decision:: Use SQLite via `bun:sqlite` for local state. In-memory mode acceptable for development.
Consequences:: Zero-config, fast, embedded. No external database dependency. But no concurrent multi-process access (irrelevant for single-process prototype). See ADR-009 for the repository pattern and test strategy.

=== ADR-005: Iframe Sandboxing for Custom Renderers

Status:: Accepted
Context:: Custom renderers are arbitrary JS code embedded in `.mediform` files. They must be isolated from the host page and from each other.
Decision:: Run custom renderers in `<iframe sandbox="allow-scripts">` with restrictive CSP. Communicate via `postMessage`.
Consequences:: Strong isolation. Renderers cannot access patient data, other questions, or the network. But iframe communication adds complexity and latency. Renderers cannot use the host page's CSS framework.

=== ADR-006: Patient and Employee Apps as Two Separate Svelte SPAs

Status:: Accepted (supersedes provisional "single SPA" decision; resolved in issue #9)
Context:: The PRD left the single-app vs. two-app question open. Two separate apps add a small amount of build complexity but keep the patient bundle free of employee code without relying on tree-shaking. A single route-split SPA would ship employee code to patients.
Decision:: Build `apps/patient` and `apps/employee` as two separate Svelte SPA packages, each with its own Vite build. Both are served as static files by the Elysia API server (`apps/api`). Patient routes are served under `/patient/`, employee routes under `/staff/`.
Consequences:: Clean bundle separation — patients never download employee code. Slightly more build configuration (two `vite build` invocations). Shared logic lives in `packages/mediform-core` and is tree-shaken per app. Acceptable for a prototype; the two-app structure also maps naturally to a future split deployment if needed.

=== ADR-007: Eden Treaty for Type-Safe API Communication

Status:: Accepted
Context:: Both Svelte SPAs need to call the Elysia API. Manual `fetch` wrappers require duplicating request/response types between backend and frontend. Type mismatches between the API contract and the client code are caught only at runtime, if at all.
Decision:: Use Eden Treaty as the API client in both the patient and employee Svelte apps. Eden Treaty derives a fully typed client from the Elysia server's route definitions, providing end-to-end type safety from route handler to UI component.
Consequences:: API contract changes are caught at compile time in both frontends. No manual type synchronization needed. Introduces a build-time dependency on the `api` package's type exports. Both SPAs must be able to import types from `apps/api` (supported by the monorepo workspace setup).

=== ADR-008: Biome for Linting and Formatting

Status:: Accepted
Context:: The project had no linter or formatter configured. Inconsistent code style across packages slows review and increases cognitive load. ESLint + Prettier is the traditional choice but requires two tools, multiple config files, and plugin management.
Decision:: Use Biome as the single tool for both linting and formatting. A single `biome.json` at the workspace root covers all packages. Biome is fast (written in Rust), requires minimal configuration, and handles both concerns in one pass.
Consequences:: Consistent code style across the monorepo with zero per-package config. Faster than ESLint + Prettier. But Biome's rule set is smaller than ESLint's ecosystem; some niche rules may not be available. Acceptable for a prototype.

=== ADR-009: SQLite with Repository Pattern (Replacing In-Memory Map)

Status:: Accepted (supersedes the in-memory `Map` implementation; refines ADR-004)
Context:: The initial prototype used an in-memory `Map<string, QuestionnaireRecord>` as the questionnaire store. This was fast to implement but data was lost on every server restart, making development workflows painful. ADR-004 already chose SQLite via `bun:sqlite` as the target; this ADR decides the migration approach and test strategy.
Decision:: Replace the in-memory `Map` with `bun:sqlite`. Introduce a repository interface that the store module implements. The interface stays stable; the implementation moves from `Map` to SQLite. Use file-based SQLite (`mediform.db`) for development and in-memory SQLite (`:memory:`) for tests. The repository is injected at startup, making the backend easy to test.
Consequences:: Data survives server restarts. Tests remain fast and isolated (each test gets a fresh in-memory database). The repository pattern adds a small abstraction layer but enables clean dependency injection. No ORM; queries use `bun:sqlite` directly.

=== ADR-010: Pre-Push Hook for Code Quality Checks

Status:: Accepted
Context:: Without automated checks, formatting and linting violations reach the remote repository and are caught only during review. This wastes reviewer time and creates noisy diffs.
Decision:: Install a pre-push Git hook (shell script or lefthook) that runs `biome check` on changed files. The hook blocks the push if violations are found.
Consequences:: Code quality issues are caught before they reach the remote. The hook runs only on changed files, keeping it fast. Developers can bypass with `--no-verify` in emergencies. No heavy tooling (no husky, no lint-staged).

== Glossary

[cols="1,3"]
|===
| Term | Definition

| `.mediform` | The custom DSL file format for defining questionnaires. Human-readable, AI-generatable, compilable to FHIR.
| AST | Abstract Syntax Tree. The in-memory representation of a parsed `.mediform` file.
| Compilation | The process of transforming a `.mediform` file (or patient responses) into FHIR resources.
| Custom renderer | A sandboxed JS function embedded in a `.mediform` file that handles user interaction for a complex question type and produces a value via `onValue()`.
| Elysia | A Bun-native, type-safe HTTP framework used for the API server.
| FHIR | Fast Healthcare Interoperability Resources. An interoperability standard for health data (R4 version used).
| FHIR Compiler | The internal module that transforms parsed `.mediform` structures into FHIR R4 JSON resources.
| HAPI FHIR | An open-source Java implementation of a FHIR server. Used for storing clinical data.
| Lifecycle Manager | The internal module that enforces questionnaire status transitions and business rules.
| LOINC | Logical Observation Identifiers Names and Codes. A standard for identifying medical observations.
| Mediform Parser | The internal module that parses `.mediform` DSL files into a structured AST.
| Observation | A FHIR resource representing a clinical measurement or finding. Created from questionnaire answers that have LOINC mappings.
| Quality Checker | The internal module that runs automated validation checks on questionnaires before review.
| Questionnaire (FHIR) | A FHIR resource representing a structured set of questions. The compilation target of a `.mediform` file.
| QuestionnaireResponse (FHIR) | A FHIR resource representing a patient's answers to a questionnaire.
| Renderer API | The contract between the host page and a custom renderer iframe: `onValue(value)` to report results, `config` for read-only question configuration.
| SNOMED | Systematized Nomenclature of Medicine. A clinical terminology system used for coding answer options.
| Svelte | A frontend framework used for the patient and employee SPAs.
|===
